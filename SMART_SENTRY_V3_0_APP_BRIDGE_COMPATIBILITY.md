# Smart Sentry v3.0 App Bridge Compatibility

This note records the current app-to-v3-bridge compatibility boundary.

## What Already Matches

The existing Smart Sentry app transport in
`app/sentry_v2/sentry_v2_comm.py` already matches the v3 bridge on these points:

- UDP host default `192.168.4.1`
- UDP port default `9000`
- wrapped JSON packet shape with fields `v`, `t`, `seq`, `ts`, `p`, and `crc`
- `cmd` message type for outbound control
- `state` message type for inbound runtime updates
- `hello` and `hb` style bench traffic can now be generated by the standalone bench tool

## Compatibility Fixes Applied

The app communication layer now explicitly supports the current v3 bridge reply shape.

- `ack` packets are now parsed from `message["p"]` first, with legacy fallback to `message["state"]`
- `cap` packets are now retained in a bridge capability snapshot
- runtime IO state now stores:
  - `switch_in`
  - `hw_arm_enabled`

## Current Switch Contract

The app can retain switch-related runtime fields, but the current Waveshare v3
bridge now reports `switch_supported=false` and does not require a dedicated
hardware switch pin.

- trigger readiness currently depends on software safety and fault state
- switch-specific UI should only appear when the capability packet says a
  switch is actually present

If a future firmware variant restores a hardware switch, the app can still
observe it through the IO runtime snapshot fields:

- `switch_in`
- `hw_arm_enabled`

## Capability Snapshot Fields

The app now retains a bridge capability snapshot with values such as:

- `role`
- `switch_supported`
- `switch_role`
- `switch_active_low`
- `switch_pullup_enabled`
- `sound_supported`
- `speaker_supported`
- `header_reference_locked`
- `pins`

## What Still Remains Outside App Integration

These are still intentionally not wired into the main app UI or behavior yet.

- support for currently unassigned outputs like LED relay, laser relay, trigger-servo PWM, and knob inputs

## Practical Next Step

After hardware bench validation, keep using the capability snapshot as the
contract boundary: if the bridge later reintroduces a physical switch, the app
should surface it only when `switch_supported=true`.
